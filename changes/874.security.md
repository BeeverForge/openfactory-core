**A Jira project is no longer handed the deployment's GitHub token.** A Jira project that named no `token_env`, on a deployment with no `JIRA_API_TOKEN`, fell through to the deployment's own pair (`OPENFACTORY_TRACKER_TOKEN`, then `OPENFACTORY_BOT_TOKEN`) and sent that GitHub token to the Jira site, which refused it as another account's; on a deployment with a GitHub App, the poller's queue scan handed it a token minted from the App instead, and the worker and the product role's board a provider of them. A vendor whose credential row names its own variable is now answered by it and by nothing after it, and a re-minting provider reaches a vendor only from its own credential row: a Jira axis reads `token_env` or `JIRA_API_TOKEN`, and with neither set the tracker says "no API token reached this tracker" and names the variable. An Azure DevOps project, which reads `AZURE_DEVOPS_PAT`, its `token_env` or the `az` login on its own, is no longer handed the GitHub token on the product role's board or in the box either. GitHub projects, and projects that name no vendor, read the pair and the App as before.
