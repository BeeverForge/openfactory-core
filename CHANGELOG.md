# Changelog

What changed in each release of OpenFactory, for the people who install it, newest first.

Every pull request carries the line its release's notes will read for it, as a fragment in
`changes/` ([CONTRIBUTING.md](CONTRIBUTING.md)). At the final release the fragments are assembled
into the version's section here, and its GitHub release page carries the same notes
([docs/RELEASING.md](docs/RELEASING.md), "The release notes"). The notes of the releases before
0.6.0 are on their [release pages](https://github.com/Open-Factory-Digital/openfactory-core/releases)
only.

## 0.6.0 (2026-10-15)

### Highlights

- **One release a week.** The cut and the first candidate on Monday, the final on Wednesday. What is merged by Monday's cut ships that Wednesday; what is not ships the week after (#530).
- **`openfactory certify`: a deployment's evidence pack.** `openfactory certify deployment` writes the pack a deployment submits to the implementation partner program: its controls computed from the deployment and its diagnostics, redacted so the practitioner is the only name it carries, and re-read before it is written; nothing is written without `--yes`. `openfactory doctor --json` and `openfactory box status --json` are the versioned documents it carries. The pack is not signed yet, and says so (#549).

### New behaviour

- **The PyPI page describes the project.** It says what OpenFactory is and is not, how to run it on one machine or as a team deployment with Docker, where each coding agent stands and what the extras add, and the suite holds every claim on it true (#368).
- **A release's notes are in `CHANGELOG.md`, and on its page.** Each pull request carries the line the notes will read for it, as a fragment in `changes/`. The final release assembles them into `CHANGELOG.md`, and its GitHub page carries them under the install block. A candidate's page carries the notes so far (#517).
- **Installing a given version, and backing up before a candidate.** (#530)
  - The README says how to install a specific version or a release candidate: by name, with `--version`. A candidate is installed only that way.
  - docs/RELEASING.md says how to back up an installation before trying a candidate, and how to go back: the two files, the Docker volumes and the two host directories the stack writes, with the commands.
- **`openfactory doctor` sees a container filling up with processes.** The new check `pid_headroom` reads what the container it runs in and the panel hold against their `pids.max`. It fails at half of it, at a hundred zombies, or when a running container is asked and does not answer, and it gives the repair. Each line names the container as its service declares it, with the new `OPENFACTORY_ROLE` that the compose file sets to `worker` and `panel` (#532).
- **Autonomy has a number.** `openfactory autonomy` and the dashboard's metrics read from each card's record how many merged cards reached the merge untouched, the rework per merged card, the repair depth, and why cards parked, classified from the recorded note. Cards whose record does not hold their start are counted apart and enter no rate, and a store that cannot be read is said, never shown as zero (#545).
- **`openfactory explain` shows where every instruction a ticket's passes receive comes from.** For a checkout, it lists in the order a job inlines them the role prompts, the constraints, each framework guideline with what the project's profile did to it, the operator's and the project's guidelines and the document index, read from the job's own context building so it cannot disagree with what a job receives; `--full` prints each block. The developer guide that teaches it is run by the suite (#548).
- **The evidence pack reads the forge.** What protects the branch the platform merges into, what the credential a job holds is granted and which releases of the platform are published are read from each project's forge, read-only; what the forge cannot answer is `unknown`, never a pass (#553).
- **`openfactory certify verify` checks a pack offline, and the pack measures its outcomes.** `verify` checks a pack the way the submissions bot does, its files, schema, checksums, signature and every threshold, each reported by id. The pack's outcomes over its window, from jobs and how they ended to cost per merged ticket, are read from the journals and the metrics store: a measure that cannot be read is null with its reason, never zero (#554).
- **The panel's page can be turned off.** `OPENFACTORY_DEFAULT_FRONT_END=off` serves the API, its two streams, the sign-in and the previews, and no page, for a deployment with screens of its own built on the same API. It is `on` by default, so an upgrade keeps the panel, and `openfactory init` writes the line (#611).
- **The API a screen of your own can rely on is documented.** `docs/reference/the-front-end-api.md` lists every route with the area a credential must hold, the three ways to present a credential, the refusals and the streams. A test keeps it equal to the code, and the panel uses nothing outside it (#612).
- **A credential for the board, and the product owner reads the board.** `OPENFACTORY_BOARD_TOKENS` / `OPENFACTORY_BOARD_TOKEN` and `openfactory people invite --board` issue a credential for the board and the rest of the floor, which is refused the product owner's area by name. The panel token stays the administrator's and reaches both, and inviting somebody stays the administrator's. A product credential now reads the board of a project with a product role, read only (#613).
- **The address decides which page opens, not the credential.** `/p/<project>/board` is the board and `/product/<project>` is the product owner's page, whoever opens them. The product owner reaches the board read only, from their page's Board tab. A board credential that opens the product owner's page is told it is refused, and given the way to its board. A page whose credential changes under it in another tab opens again as the page that credential may see (#614).
- **The product owner can put a card in the queue from their own page.** A card nobody has started, opened on the product owner's page (from its Board tab, or from the board they read since #562), offers **Queue it**, in the board's own name for the queue. The page asks first, because from the queue the factory picks the card up and starts spending. The press is the row a yes to a queue proposal already reached (`product_promote`), with the same gate: only a person listed among the product's admins may start work. Anyone else sees, in place of the button, that starting is an approver's yes (#637).

### Fixes

- **A confirmed queue runs in the order a person approved.** The factory did not necessarily start with the first card of a confirmed queue: the local board served the queue by card number, and on Jira moving a card into the queue left its rank where it was. The cards are now ranked on the board in the approved order, and the reply says when a board cannot rank or refused a rank (#512).
- **Every answer to the product role's writes speaks the conversation's language.** Refining, closing, removing, correcting or aligning a card, a capability, a breakdown, a queue and the release's refusals answered in Portuguese only, and some named a Jira card `#KEY`; they now answer in the conversation's language and name a card as its tracker does (#513).
- **On Jira, a backlog order is stated by the cards' keys.** The order a person confirmed in the conversation was read as digits only, so an order of Jira keys could not be stated; it is now read by the tracker's own keys (#515).
- **A card in a column no stage is is refused with the line that maps it.** On an Azure DevOps board with a stock process every new work item lands in `New`, which maps to no stage, and the first card's queueing was refused in English with no fix named. The refusal now speaks the conversation's language and gives the tracker option line that maps the column, quoted as the registry takes it, and `openfactory doctor` names every unmapped column and a board with no backlog (#521).
- **The installer's preflight reaches Docker Desktop's daemon.** On macOS with Docker Desktop the preflight said the daemon did not answer, one step after the installer had pulled every image through it, and skipped the two checks that need it: the preflight's container was given the host socket's group, while Docker Desktop hands a container a socket owned by group 0. The installer now gives it the group a container sees, and a refused socket is named as a refusal, not as a daemon that gave no answer (#529).
- **A release candidate's page installs the candidate.** It printed the one-line install, which installs the latest final release, so the page of v0.5.0-rc.1 told its testers to install v0.4.2. A candidate's page now gives its own installer with `--version`, the upgrade of an existing installation with `--force`, and the way back. A final's page gives the one-line install (#531).
- **The worker and the panel reap the processes they inherit.** Their PID 1 was our Python process, which reaps no orphan, so every child git's detached maintenance left behind stayed a zombie for the container's life: a panel ran out of processes after 39 hours of use and read the engine as unreachable until it was restarted. Every container whose PID 1 is ours now starts an init: `init: true` in `docker-compose.yml`, `docker run --init` for the box, and `tini` as the worker and sandbox images' entrypoint, for a runtime that adds none (#532).
- **Forgetting a project closes the engine runs that still held what was said.** After `project forget` or `project forget-conversations`, the product's conversation runs in the durable engine stayed open, holding the forgotten messages and replies where the engine's retention never reaches them. Both commands now close the product's conversation runs that no turn is at work in, and `project forget` the project's tech-lead run too; the report says when their history expires, and the next message starts a new run (#533).
- **Closing a finished card says it was delivered.** A card the product role filed, closed from Done, was recorded as delivered and answered that it "stays in the history as not done"; the answer and the close control now say the word the close records — delivered from a finished column, not done from any other (#534).
- **A card the product role files is never born in the pickup column.** On an Azure DevOps board with no backlog state, the setup guide's own Basic process among them, a filed card was created in `To Do`, the pickup column, and could be picked up and built with nobody queueing it. The card is now created in the backlog the deployment declares, the product role files nothing where it would be born in the queue and says why, and `openfactory doctor` fails `board_intake` with the lines that repair the board (#536).
- **The notes the product role writes on a card speak the project's language.** The notes on closing, aligning, re-pointing and refining a card, the signature that heads them and the capability write's refusals were Portuguese only; they are now written in the project's language, and a failed git step of the capability write no longer puts git's output in front of the person (#538).
- **A card is never born in the pickup column, whoever creates it.** Every writer of a new card — the board's own new card, a split's children, the factory's impediment card and `preview propose --as-card`, as well as the product role — first asks where the card would start, and creates nothing where it would be picked up and built with nobody queueing it. On Jira, where a new issue starts is read only when it cannot be a guess: a workflow with several statuses a new issue could start in names the one with the new tracker option `intake_status`, and `openfactory doctor` fails `board_intake` until it does. A declared status or state the tracker's type does not have is refused the same way (#543).
- **A card's notes name the platform in the project's language.** The notes the card's door writes said "_Fechado por the workflow._" on a Portuguese project — the code's own name for whoever made the change. The platform is now named in the project's language, with Portuguese's contractions ("pela fábrica"), and a person by their name, as before (#546).
- **A one-machine deployment's jobs say how they ended.** `openfactory run` and `openfactory poll` now write the ending line the workflow writes, through the same function, so `openfactory certify` and every reading of the factory's outcomes count the jobs they ran; before, each of them read as never ended (#551).
- **An upgrade's preflight sees the agent credential `.env.compose` holds.** `install.sh --force` reported `FAIL agent_credential` and asked for a new token while the file held one that worked, because the check read only the installer's environment. Every check of a deployment setting now reads `.env.compose` under the environment, as compose does, so an upgrade also checks the ports it moved (#560).
- **Accepting or breaking down a requirement from the panel says which fronts were not filed.** The answer named only the cards that landed, so a front the automatic review refused, or that the breakdown ran out of time for, was dropped without a word whenever another one landed. Both now answer as the conversation does: what landed, what already existed, and what was not filed and why (#564).
- **The product chat shows the whole conversation, a page at a time.** Reopening a conversation on the panel showed only its last turns, about 6,000 characters, and a conversation older than the product's last 300 lines opened empty. The panel now opens on the newest 40 turns, with an **Earlier messages** button at the top that brings the 40 before them, back to the start. `product_thread` takes the same cursor as `before`. What the product role is given to answer from is unchanged. On the first start after the upgrade, the worker and the panel add an index to the metrics database, which pauses once on a large one (#566).
- **A breakdown no longer files a card on top of one it did not file.** When a requirement is broken into cards, the product role now says which cards build on which. If a card is not opened (refused by the automatic review, out of time, or failed to file), every card that builds on it is held too. The reply names both: "X was not opened, so I held Y, which builds on it". Asking for the breakdown again opens them in order. The reply now names every card that was not opened, not only the first (#576).
- **A capability confirmed in the conversation is committed to the context repository in English.** Its commit message was Portuguese on every project, whatever the project speaks (#579).
- **A deployment that runs on the agent token pool alone passes the installer's preflight.** The pool is `OPENFACTORY_AGENT_TOKENS`, which the worker reads first. The preflight did not know it. An upgrade of such a deployment was told that no agent credential was visible and was sent to replace a token that worked. Each harness now says which settings it authenticates with, and `openfactory preflight` and `openfactory doctor` both ask it. A pool that cannot be read is named as such, and so is the missing failover when a single token is left. A harness that signs in through its own login is no longer failed for a missing variable (#582).
- **The deployment's settings file is read the way it was written, and a file that cannot be read says so.** `openfactory preflight` read `.env.compose` with rules of its own. A row edited by hand, such as `PANEL_PORT=8788  # moved` or `export ANTHROPIC_API_KEY=…`, was misread, and the preflight then checked the default port or reported no credential. Every reader of the file now uses the same rules as the CLI. A file that is there but cannot be read, for example root-owned after a `sudo` run, now fails the `env_file` check with the repair. The credential check no longer reports that nothing is set (#583).
- **`openfactory certify deployment` refuses an address typed as the practitioner.** The practitioner is the one name a pack keeps, and it was kept past every rule. An e-mail address, URL or host typed into `--practitioner` reached `pack.json` and `summary.md`. It is now refused by the flag's name, before anything is read. `redactions.json` also lists the partner and the profile among the fields kept as typed (#588).
- **`openfactory autonomy` exits 2 with what failed when the metrics store cannot be read, whatever the store.** Before, a store added by an add-on that raised its own error printed a traceback instead (#589).

  The states past the merge are now a slice of the job states' own order, held by a test to the eight a delivery passes through, so a reorder of the states cannot quietly count a failed job as landed. The operator's remedy for a park of class `gate` is checked again: a test's own copy of the classes had lost it.
- **When the repository cache cannot clone a repository, its log line carries git's whole message.** It used to keep only the last 160 characters, which cut inside a file path and lost what git had been doing when it failed (#592).
- **A clone of a repository on the same machine no longer fails while git repacks that repository in the background.** Every clone the platform runs now reads through git's transfer protocol rather than copying the repository's object files one by one. This affects the local forge's repositories, the worker's cache, and the box and preview workspaces cloned from it. With newer git (seen on 2.55 and 2.56), those copies could fail with `hardlink different from source` or `failed to copy file`, because git's automatic maintenance repacks small repositories after a commit, push or fetch (#594).
- **Accepting a requirement, or asking for its breakdown, while a breakdown of it is already running no longer says that nothing was filed.** The panel, the CLI and the API now say the breakdown was already running, start no second one, and list the cards the running one filed (#601).
- **A close in favour of another card names what only the closed card carries, before the yes.** The product role offered to close one card "or" another as if they were equal, and its confirmation said the two ask for the same thing: it had compared them by title. The confirmation now lists the acceptance criteria the closed card states and the other does not, and the requirement only the closed card executes. When the two cards cannot be read, the question says so, so the person opens both first (#602).
- **The product role acts on a requirement however the person says it.** Agreeing to a requirement, dropping it, writing a decision into it and noting a fact were reached only by fixed sentences such as "aceita o requisito 66". "pode aceitar o 66" or "sim, concordo com o requisito 66" reached nothing, and the role, which had understood, had no way to act. The role now proposes each of the four from what it understood, and the person confirms it as before; a drop's question shows the reason that will be written in their name. A fixed sentence no longer acts by itself (#603).
- **The product role finds open cards by what they say.** The product's memory indexed closed cards only, so a question about two open cards was answered from their titles. On a live run the role advised closing the only card that carried a requirement's first front. Open cards are now indexed with their bodies, marked open as the board last showed them, and a card that opens or closes is updated with it (#606).
- **The queue is proposed from what each card asks.** The product role ordered the backlog from card titles alone, while being asked to hold back work that depends on something not done. Each candidate now reaches it with what it asks, the requirement it executes and its first acceptance criteria, bounded per card (#607).
- **A delivery's answer is told in the project's language.** When a person answered "did it work?", or was reminded to answer, the reply was Portuguese whatever language the project spoke: an English client who said "yes, it works" was thanked with "Ótimo — considero encerrado então". The reply, the reminder and the name of the delivery they refer to now follow the project's language (#609).
- **A requirement asked to be broken down from the conversation is broken down once, whichever door asked.** Asking the product role to break a requirement into tasks, or saying yes to accepting it, now starts the same breakdown the panel and the command line start, so a second one is not started beside it. The conversation is answered at once that the breakdown began — or that one was already running — and is told what became a card when it ends, in its own language (#616).
- **A card asked for in the conversation for an agreed requirement is no longer filed beside its breakdown.** When a requested card names an agreed requirement (`REQ-0066` in its title or text), the product role does not open it: the work of an agreed requirement comes in through its breakdown. It says instead that the breakdown is running, lists the cards that already carry the requirement's work, or offers the breakdown in the words that start it (#617).
- **A front a breakdown did not file stays on the requirement's row, beside the retry.** When a breakdown leaves a front out — the review refused it, its time ran out — the requirement's row on the product page now says so, with the reason, until the requirement's next breakdown; it used to be said once, in a notice that disappeared in seconds, while the row looked like everything had been filed (#621).
- **A requirement's breakdown no longer files work its own cards already carry, or work filed while it ran.** The breakdown now reads the cards that already execute the requirement, open and closed, in their own words, and drafts only what they do not carry: a delivered requirement does not get its work filed again. Just before each card, it asks the board again, and a card of the requirement opened in the meantime holds the rest of the breakdown, which names that card (#629).
- **Closing a card in favour of another no longer claims the two ask for the same thing when the closed card states nothing to compare.** A card with no acceptance criteria and no requirement it executes cannot be compared with the one that stays, and the question asked before the yes now says so, instead of saying they ask for the same thing (#630).
- **What the product owner writes in a project's documentation repository, and what it says about it, is in the project's language.** On a project that speaks English, a missing requirement used to be answered in Portuguese, and the documentation repository took commits and pull requests titled in Portuguese ("requisito 0002: abandonado por …", "Levantamento inicial: …"). Those writes and their answers now follow the project's language. So do the fact files, the note on a card held back because its automatic review did not answer, a decision row's conversation, a case's reading and the tech lead's note on a remedy that never worked. A reason given in English when closing a card ("close #511 because …") is now recorded on the card (#632).
- **The product role knows when a requirement is already being broken into tasks, and a breakdown started from the panel is told in the conversation the requirement came from.** For each agreed requirement, the role now reads whether its breakdown is running and which cards already carry its work, so it points there or offers the breakdown instead of proposing a separate card. Accepting a requirement, or asking for its breakdown, from the panel, the command line or the API now also tells the conversation the requirement was asked in what was filed (#633).
- **The product role closes, corrects and aligns a card however the person says it, and asks before it breaks a requirement down.** Closing a card, correcting its text or title, aligning it to an agreed requirement and writing its criteria were reached only by fixed sentences such as "fecha o #511", and those sentences could not even read a card number longer than four digits. "pode fechar o final 9" reached nothing, and the role, which had understood, told the person only they could close the card. The role now proposes each of these from what it understood, naming the card as the board spells it, and the person confirms it as before. Breaking a requirement into cards and writing a card's criteria used to happen as soon as a sentence matched; they now wait for a yes like every other write, so "ok, pode escrever o card" about an agreed requirement is proposed as its breakdown instead of filing a card of its own (#634).
- **A card the product role writes cites each file as its repository reads it.** The role reads the product's code in a view that places every source repository at `src/<name>/`, and it wrote its cards that way: a card filed in `jornada` cited `src/jornada/tasks/store.py` where the repository has `tasks/store.py`, so the review could not check the criterion that named it and parked the job for a person. A breakdown's cards, a card a person asks for, a defect, and the criteria a refinement, an alignment or a correction writes now cite each file from the root of the repository the card is in, and a file of another repository of the product by that repository's name (#654).
- **The product owner answers a person in the language they wrote in.** On a project set to `pt-BR`, an English question was answered in Portuguese. Every harness already told the model to reply in the writer's language, but the product owner's own prompt then said "Write in BRAZILIAN Portuguese … the reader is Brazilian", and the more specific rule won. Its language rule now says first to answer in the language the person wrote in. The dialect rule still governs what the product owner says first and its replies to anyone who writes in the project's language. A card drafted in the conversation's language keeps the dialect rule alone, because a card is not a reply (#655).
- **Two processes on one machine no longer change the same repository checkout at the same time.** The repository cache held its lock per process, so on a deployment where the panel and the worker run on the same host, both could sync one project's checkout at once. One process deleted and re-cloned the checkout the other was resetting, git failed with "already exists and is not an empty directory", and a fresh project was filed an impediment card. The lock on each cached checkout is now a file lock that every thread and every process sharing the cache directory respects. A process that dies while holding it releases it, and a sync that cannot have it within thirty minutes gives up and says so, as any failed sync does. The compose deployment was not affected: only its worker uses the cache (#656).
- **A project's floor no longer says its next card will be picked up while every job slot of the deployment is held, and a parked job says what it holds.** A job parked for a person still holds its slot, and the floor counted only its own project's jobs. With the default single slot, a park on one project held every other project's cards for hours while their floors said "Armed — the next card will be picked up", and the product owner could not say why To Do did not move. A floor now says the next card waits for a slot, without naming another project's job, and says what frees it. The product owner is told that a live job holds a slot and that an impediment's deadline sets the card aside rather than waking it. `merge`, `adjust` and `discard` asked of a parked job now say to answer it with `resume` or `skip` (#660).
- **A proposal adjusted before the yes keeps what the person asked for.** The product role wrote a requirement draft from the person's last message alone. So when someone asked for a CSV export filtered in the API and in the client's currency, and then added "filter by status too", the draft that replaced it was a filter on the screen's list, while the reply above it said the rest of the proposal was unchanged; the export and the currency were in no requirement. Every draft — a requirement, a card a person asks for, a defect — is now written from the conversation, the role's reply, and the draft it replaces, whether that draft is still waiting for the yes or the person's "no" just took it off the table; the drafter is told to keep everything the person did not change (#661).
- **A card names its context repository without a path of the operator's machine.** On the local row, every card the product role filed from a requirement linked the context repository to its directory on the machine, `~/.openfactory/context/<name>`, which nobody reading the board can open and which wrote the operator's home directory, account name included, into every card. A card now links the context repository only by an `http://` or `https://` address, as it does on a hosted forge, and otherwise names it as plain text (#662).
- **Every project of a product of several projects is linked to its context repository.** Several registry projects that point at one context repository are one product, but the product link compared the context's `product:` with each project's name, so only one project could ever pass: `doctor` failed `product_link` on the others, the product role could not read the product's requirements from them, and an impediment card was filed on each of their boards. A project is now linked when the context lists its code repository in `sources:`, written the same way, whatever the product is called. A project the context does not list is still refused, and the product's name alone admits a project only when it is the project's own name (#663).
- **On the local row, a product of several projects reads each project's code where that project lives.** The local forge answered any repository name that was not its own project's as a context repository under `~/.openfactory/context/`, so another project of the same product was looked for where it does not exist: onboarding could not clone it, every conversation logged a failed sync, an impediment card said the product agent could not open the product's code, and the product role told the person it could not read that repository. A registered local project of the same product is now read at its own `repo_path`. A project of another product, or of none, is never read as a member, and a context repository is still the installation's own (#664).
- **A card of another repository of the product is never run in this project's repository.** On a board that keeps every card in one place, a breakdown's front meant for another repository of the product was filed on this project's board with nothing recording where it belonged, so queueing it ran its job in this project's repository: the agent changed nothing, no pull request was opened, and the park held the deployment's only job slot for hours. Such a card now records the repository it belongs to (`belongs_to:` in its front matter, and a sentence a person reads), and it is refused when queued, taken out of the queue if it reaches it another way, and parked at pre-flight if a job starts on it regardless, each time with a sentence naming the repository it belongs to (#665).
- **A refusal names the people who can do what was refused.** Someone the product does not let approve, asking the product owner to accept a requirement and break it down, was told "ask one of these people to confirm and I'll record it", with nobody named, about an act that was not the one refused, and with a promise nothing was waiting on. Every sentence that sends a person to the product's approvers now names them, as the product's admin list has them and at most three. That covers the refusal itself, a card's close or removal, putting a card in the queue, sending a change back, accepting it, and the line asking the requester to tell the room they tried it. When nobody can approve yet, it names who can set that up. The refusal also no longer says which act it was, and promises nothing (#666).
- **A late yes typed in a project's room is told that its proposal expired, and nobody is asked a question no yes of theirs can answer.** The panel writes `@po` in front of every message typed in a room, and the platform read "@po sim" as neither a yes nor a no, so a person who confirmed after a proposal expired was never told, and the product role proposed the same thing again in their name. A yes or a no is now read without the mention that addressed it. And where the person asking may not act and no admin may confirm on their behalf, every act the role proposes is refused at once, naming who can: agreeing to a requirement, dropping it, recording a decision, noting a fact, closing, correcting, retitling or aligning a card, refining it and breaking a requirement down. Before, only the breakdown and the refinement were refused; the others waited for a yes that could never come. Where an admin may confirm, an agreement now names them under the question, as every other act did (#667).
- **A card the factory has taken up says why it offers no Send back.** On the owner's page, a card waiting at the human merge gate could show neither the Send back button nor any sentence, when the engine had not yet published its gate or could not be reached. Whoever opened it was left guessing. The card now always says why: the change is not waiting on them yet, the engine could not be asked, the passes are spent, or only the person who asked for it or an approver can send it back. Reading an engine error as "no job ever ran for this card" is now written in the log (#668).
- **A small fix to how something is shown or worded, asked for in the conversation, becomes a card on one yes.** "The date shows as 2026-11-03, we read dd/mm/aaaa — can you fix it?" was argued into a requirement: written on one yes, agreed on a second, and only then broken down, so nothing reached the board for a one-line fix. The product owner is now told that a small change to how something the product already does is shown or worded (a date or number format, a label, a message's wording, the order of a list) is a card the person asked for, as long as it contradicts no agreed requirement. A change to what the product does is still argued into a requirement (#669).
- **The product role no longer shows a proposal for a yes while it still needs answers that would change it.** Asked for something only the person could settle — which currency, whether a filter applies to the screen or to the file — the role wrote "I need two answers before I close the text" and, under it in the same message, a proposal with a yes button that had already chosen both answers for them. The draft now says what it cannot be written without; while it does, nothing is proposed, the person is asked, and anything already waiting for their yes stays as it was. A proposal that leaves other questions open now says, under it, that they can be answered after reading the text (#670).
- **An impediment the factory files on a person's own board is titled in the project's language.** On a deployment where the factory's own cards land on the product's board — every local installation, and a factory board declared on the product's own tracker — an impediment was titled in English beside a Portuguese team's own cards, such as "[openfactory] reservas-web: the product's requirements cannot be read". It is now titled in the project's language there. A factory board of its own keeps the one spelling it always had. An impediment already open under either spelling is still recognised: it is not filed again when the language changes, and it closes when the capability works again (#671).
- **What the product owner tells a person, and the requirements it drafts, cite each file as its repository reads it.** After the cards were fixed, the product owner's replies and requirements still cited files the way its own view of the product places them, under `src/<name>/`: a reply said `src/reservas-web/reservas_web/pages.py:7` for a repository with no `src/`, and a requirement committed to the documentation repository cited `src/jornada/tasks/store.py` for `tasks/store.py`. Replies, requirement drafts (every field, the conflicts' explanations included), the classification of parked cards and the proposed queue now cite each file from the root of its repository. In a product of several repositories, each path names its repository (#672).
- **The members of one product publish their knowledge maps one after another, and a publish no longer makes a person's save fail.** The projects of one product refresh their knowledge on one clock, so their module maps were published into the shared context repository at the same second. The publish took no lock and retried once: with three members, the third map was rejected twice and dropped until the next refresh. The same publish could also land between a person's clone and their push of a requirement, a decision or a fact, and those writes push only once, so the person's save failed. Every publish of derived knowledge now holds the product's semaphore around its clone, its commit and its push, as the system layer's already did. A publish that cannot have the semaphore in time publishes nothing, logs it, and leaves it to the next refresh. `openfactory forget --with-context` now holds the semaphore too when it removes the conversations' distillates (#673).
- **An engine that does not answer in time is a 503 that says so, from every route of the panel and every action, never a 500 with a traceback.** `/api/inbox`, `/api/coordinator/messages` and `/api/decisions` caught only a failed connection, so a read that ran out of time escaped them as a 500 and a ~200-line traceback in the log: 103 of them in one half hour of a long test run. An action whose read ran out of time, such as `diagnose`, answered 500 too. Every route and every action now answers 503 with the read's own sentence, and the log carries one line for it (#674).
- **The worker's and the panel's logs carry a time, a level and a source on every line, and keep the platform's INFO lines.** Neither process set its log up, so a warning reached the log as its bare message, with no time, level or source, and every INFO line was dropped: a context push rejected twice showed one line, and failures could be placed in time only from the engine's own history. Every line is now `<UTC time> <LEVEL> <logger>: <message>`, the panel's request lines included, and `OPENFACTORY_LOG_LEVEL` sets the platform's level (`INFO` when unset). Libraries stay at `WARNING` (#675).
- **A proposal tells each conflict for what it is.** Every conflict the product owner raised before a yes was framed as going against something already decided, "a change of mind, not an addition", whatever the drafter had recorded. A date format that only added detail to an agreed requirement was told to the person as a change of mind. A contradiction is still told that way; a request that repeats, adds detail to or builds on an agreed requirement is now told in its own words, and a proposal with several kinds of conflict says each under its own (#676).
- **What the automatic review found reaches a person in their own language.** When a card from a requirement's breakdown did not pass the automatic review, the conversation and the owner's page said what was missing in the review's English instructions to the drafter, inside a Portuguese sentence: "O que falta: Name the reservations screen …". A card shown for a yes while the review still disputed it quoted the same English. A person now reads the review's findings in the project's language. The review writes a line for the person beside the ones it writes for the redraft, and the platform's own checks have a sentence in each language. When the review gave no such line, the person is told so in their language. The redraft still receives the findings as they are (#677).

### Security

- **An agent role reaches only the tools it is given.** Every harness started every role — the product role that answers people, the executor, the tech lead and the reviewer — with the MCP servers of the account running it beside the role's own tools: that account's hosted connectors, its plugins' servers and its own MCP configuration. Now every command the platform hands a harness starts it with none. Claude Code, the native reviewer included, carries an empty, strict MCP configuration. Codex leaves the account's `config.toml` unread and still reads the login. OpenCode is handed a configuration directory made for the run, empty and removed when it ends, with `OPENCODE_CONFIG` and `OPENCODE_CONFIG_DIR` emptied. Kimi Code, which cannot be started without the account's servers, is not started while `~/.kimi-code/mcp.json` or an installed plugin declares one, and neither is OpenCode while `~/.opencode/opencode.json` exists; the person reads which file held the role back and what to do.
