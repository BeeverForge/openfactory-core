# Changelog

What changed in each release of OpenFactory, for the people who install it, newest first.

Every pull request carries the line its release's notes will read for it, as a fragment in
`changes/` ([CONTRIBUTING.md](CONTRIBUTING.md)). At the final release the fragments are assembled
into the version's section here, and its GitHub release page carries the same notes
([docs/RELEASING.md](docs/RELEASING.md), "The release notes"). The notes of the releases before
0.6.0 are on their [release pages](https://github.com/Open-Factory-Digital/openfactory-core/releases)
only.

## 0.7.0 (2026-10-28)

### Highlights

- **OpenFactory 0.7 is the last OpenFactory release: the project continues as BeeverForge.** BeeverForge's first release, 0.1.0, comes next, from [BeeverForge/beeverforge-oss](https://github.com/BeeverForge/beeverforge-oss). Until BeeverForge 1.0 ships, `release/0.7` receives security fixes only, as 0.7.x patches, and no other OpenFactory line receives any fix; `SECURITY.md` says so (#1126).

### New behaviour

- **A job's prompt has one budget, and what it leaves out is named in it.** The documents a pass inlines — decision records, the framework's, the operator's and the project's guidelines — share one budget with the card, the plan, the knowledge map and a repair's failure log, 160,000 bytes unless `OPENFACTORY_PROMPT_BUDGET` says otherwise; the project's own guidelines are kept first and decision records newest first, and every document left out, or cut at 8,000 characters, is named in the prompt by the path the agent can open it at. `openfactory explain`, `doctor` and `box prove` say what the budget keeps (#364).
- **The product role's next turn inside a minute asks no forge about the product's sources, and an operator sets how many are brought up at once.** A source brought up less than `OPENFACTORY_SOURCES_FRESH_SECONDS` ago (60 when unset; `0` asks every turn) is served as it was, so a change pushed in that window reaches the role on the first turn after it; `OPENFACTORY_SOURCES_PARALLEL` (8 when unset) sets how many of a product's sources are brought up side by side, for a turn and for the system layer's refresh. A cache carried across the upgrade has no window yet, so its first turn asks every forge as before (#369).
- **A pull request says what the agent says it did.** Its description now ends with the implementing agent's own final message, quoted under `## What the agent says it did` and labelled as the agent's claim, with its code, HTML, emphasis and headings shown literally and a bare link shown as code, bounded in length with a line saying when it was cut, and each later repair or adjust pass adds one short line of its own beneath it; on a forge that limits a description's length, such as Azure Repos, the oldest of those lines give way first and are counted, so the cost line, the review and the newest pass remain whenever the rest of the description fits. A credential in the agent's words — a forge or vendor token, the value of an `Authorization` header, a password in a URL, or a secret the factory itself holds — is shown as `[credential withheld]`. The independent reviewer is still not shown any of it, and a card criterion that asks the agent to report something in writing is now left for the person to read there instead of being marked as failed (#627).
- **Each read of the API declares the shape it answers in.** The floor, the jobs, a job's detail, the board, attention, the inbox, the budget, the decisions, the loops, the messages, the product room, its documents, the metrics, whoami and the action catalogue each name their fields in the description the API serves, so a front end of one's own no longer has to read the panel to learn them. The bodies are unchanged: a key no field names, a number as it was computed, and a row that lacks a field or carries a null are answered as before. A value of another type than its field declares is no longer passed through: it is converted where the model can (`"3"` becomes `3`, `"yes"` becomes `true`), and a value it cannot convert fails the read (#678).
- **A running deployment says whether it is alive, whether it can work, and which version it runs, and its logs can be JSON lines.** `/healthz` answers 200 while a process serves, and `/readyz` answers 200 when the durable engine answers, the registry reads and the identity provider can admit, or 503 naming each check that failed; neither needs a credential, the panel answers both on its own port and the worker on `OPENFACTORY_HEALTH_PORT`. The compose file uses `/readyz` as the worker's and the panel's healthcheck, so a process that cannot reach the engine is reported unhealthy instead of running. `GET /api/v1/version` answers the package version, the image the process runs from, the kind of address the engine is reached at, and every installed add-on with its distribution, version, axis and kind. With `OPENFACTORY_LOG_FORMAT=json` the worker and the panel write one JSON object per line, with `ts`, `level`, `logger` and `message`, plus `project` and `product` when the record concerns one and `deployment` when `OPENFACTORY_DEPLOYMENT` names it; the default format is unchanged. The compose healthchecks ask every 15 seconds, so the panel's log gains one `uvicorn.access` line per probe in either format, and the worker's says once where it answers and once when a check starts failing (#681).
- **The command line changes the installation only through its actions, which a front end of one's own reaches too.** `openfactory onboard` now creates a missing context repository through the `product_init` action, as `product init --create-context` does, and so records who ran it like every other change to the installation; its flags, its output and its exit codes are unchanged, except that a forge which cannot create a repository is said in the action's sentence (#741).
  - `GET /api/v1/actions` marks each row that changes the installation with `installation: true`, so a screen of one's own can leave those rows out for a credential scoped to the board or the product, which is refused them.
- **A stored credential can come from a mounted file, and the box image can be pulled with a credential of its own.** Every secret the factory reads now comes through one credential store, named by a reference: a variable name as before, `env:<NAME>`, `file:<name>` for a file in `OPENFACTORY_CREDENTIAL_DIR`, or `<kind>:<name>` for a store an installed add-on declares (`credential_store.<kind>`) (#742).
  - Set `OPENFACTORY_CREDENTIAL_STORE=file` and `OPENFACTORY_CREDENTIAL_DIR=/run/secrets` to read the factory's own credentials (the harness tokens, the GitHub App key, the bot and per-axis tokens, the panel's tokens, the engine's key) from files named like their variables; a variable still answers where no file does, so secrets can move one at a time.
  - A project's `token_env` may name a reference, such as `token_env: file:acme-jira`.
  - A file is read at each use and refused, by name and with no fallback to the variable, when anyone but its owner can write to it, to the directory it is in or to a directory one of its name's links is in, or to any directory between those and the credential directory (on a mount that accepts writes). It is also refused when it has more than one name, when a link on its name's way was made by another user, when its name leads through more than 40 links or out of the directory, when it is not a regular file, or when it is larger than 64 KB. A directory others may write to is read only on a mount that refuses writes, as a cluster mounts its secret volume, and only when it and the files read through it belong to root or to the deployment's user.
  - `box.pull_credential` (a reference) and `box.pull_username` give a project's box image its registry login: it is used for that one pull, from a client configuration deleted afterwards, and never reaches the box or the worker's shared docker configuration.
  - `openfactory doctor` has a `credential_store` line naming where credentials come from and every reference the project names, by reference and store, never by value, and failing every credential the store refuses, each with its repair.
  - A refusal is final: nothing is used in its place, not the variable, not the next name a credential falls back to, not a mint or a login. A refused panel token keeps the panel closed, and a refused harness credential stops the agent rather than letting it run on another.
  - A secret file on a read-only mount, such as compose's `secrets:`, is read whatever its write bits; keep it `chmod 600` on the host.
  - A box image pulled with its credential goes to the docker daemon the box runs on, on a non-default docker context too.
  - A remote box whose launcher declares nothing is handed short-lived minted tokens only: a forge or tracker secret held in the credential store is refused for it by name, and a variable the box reads for itself is handed over by name as before.
  - What the credential stores hold is withheld from the product's facts and briefings, as the values of the environment's secret-named variables are; and the doctor's `credential_store` line says when the box image's pull credential is the forge's own token, which writes where a pull only reads.
  - An add-on credential store whose builder fails, such as one installed and never configured, is refused by name wherever a reference or `OPENFACTORY_CREDENTIAL_STORE` names it, and is passed over by everything that only withholds what the stores hold.
- **`openfactory doctor` checks that a deployment serves one GitHub organisation.** A new `installation_scope` line asks the configured GitHub App which organisation it is installed on and fails, naming both organisations, the projects in each and the repair, when the registry names another one or spans more than one; with a registry in one organisation and no App configured, or an App beside a static token that every GitHub project uses instead, it says the check does not apply and asks the App nothing. The reason for the rule, and how to run one deployment per organisation, is in the configuration reference (#743).
- **Several projects can share one Jira project.** A Jira tracker takes `scope_jql`, a JQL condition such as `labels = "of-api"`, and the project's pickup queue, its board as the panel and the product role read it, and the search for an already filed ticket of the same title are limited to the issues it selects, so one project no longer picks up or reuses another's tickets. The condition is ANDed in parentheses, so an `OR` inside it cannot widen the read past the project; a condition Jira refuses reads as an unreadable board and the warning names it. A scoped project refuses, by name, to edit, close, remove, queue or rank a card outside its slice: another project's, which is that project's to act on, or one it filed that the scope does not select. Starting a job on a card, reopening a closed card and commenting on one still reach any card of the Jira project by key. Unset, the whole Jira project is read as before (#752).
- **A pull request waiting on a person, for their review or for the click that merges it, can have a column of its own, apart from the cards that are stuck.** The factory now sends it to the lifecycle key `needs_review`, and a board that has a column for that key puts it there instead of in Needs Action; the board reads a card there as waiting on a person, and the factory's own review may have rejected it. A board with no such column keeps putting these pull requests in Needs Action, as before. Needs Review covers the whole human gate at the pull request, the review and the merge click: the factory has one gate there and does not tell the two waits apart, so a pull request a person approved and has yet to merge stays in Needs Review until it is merged. A board `openfactory project init` creates from now on has seven columns, with Needs Review between In review and Needs Action. Triage's *waiting too long* finding covers a pull request left in Needs Review; the product role's review of parked cards does not list it (#753).
- **A red check whose failing log names no file the pull request changes is re-run before an agent is paid to repair it.** On GitHub the failed jobs are re-run once and the pull request says which and why; a repair pass that changed nothing re-runs them once too, both count against the same repair limit as before, and a forge that cannot re-run jobs repairs as it always did (#756).
- **Every refusal of an action says why in a word a program can read.** A refused action answers `data.reason` beside its `code`: the code itself where nothing finer applies, and otherwise one of `bad_parameters`, `bad_ref`, `out_of_scope`, `not_the_installations`, `not_admin`, `no_code_yet`, `engine_unreachable`, `raised`, `reported_nothing` or, for a name no action has, `unknown_action` — so a credential scoped away from an area and an actor who is not an admin, both `denied`, are told apart. `/api/actions` lists each action's possible reasons as `refusals` (#837).
- **Pausing pickup, naming and declaring a product, revoking a person and running the doctor are actions.** A front end of one's own reaches each with `POST /api/act/{name}` — `poller_pause`, `poller_resume`, `product_name`, `product_declare`, `people_revoke` and `doctor`, whose data is the `openfactory.doctor/1` document — and the command line's verbs map onto the same rows, with their flags and their success output unchanged — `poller pause` and `poller resume` now print a refusal on stderr, where the missing-engine one already went (#839).
  - `openfactory people revoke <id>` is new: it ends a person's registration, every session they hold and any invitation still open for them, records who did it, and refuses the last person registered while no credential closes the panel's door.
  - Changing the installation is the administrator's: a credential scoped to the board or to the product is refused these rows and `people_invite` with a 403.
- **A project's model, language, preview policy and removal are actions.** A front end of one's own changes them with `POST /api/act/{name}` — `project_set_model`, `project_set_language`, `project_set_preview` and `project_remove` — and `openfactory project set-model`, `set-language`, `set-preview` and `remove` map onto the same rows with their flags, exit codes and success output unchanged; like every row that changes the installation, they are refused to a credential scoped to the board or the product (#840).
  - A model value is saved verbatim as before, with one exception: a value that begins with `-` is refused with a sentence where a project's model is set through the registry — `project set-model`, `project add --model` and the registry file. Every harness is handed the model as a single `--model=<value>` token; that one-token form is what holds a value from `OPENFACTORY_<ROLE>_MODEL`, which is read directly and not through the registry.
- **A remote box's launcher can declare that it resolves credential references itself, and it is then handed the reference to a stored secret, never the secret.** A launcher declares it with `resolves_references = True` and a `launch` that takes the `references` keyword; one that declares without taking it is refused by name when the box is first asked for. A launcher that declares nothing is handed only short-lived minted tokens, and a credential held in the credential store is refused for it, before anything is launched, in a sentence that names the box and the declaration it lacks. `openfactory doctor` has a `launcher_credentials` line saying, for each remote box, whether its launcher receives references or values, or that its runner is not installed here; it fails when this deployment's box has a launcher that declares nothing and a project's forge or tracker secret is held in the credential store, naming the reference, never the value (#903).
- **Four more reads of the API are typed and served under `/api/v1/`, and the rest are named.** `GET /api/v1/projects`, `GET /api/v1/address`, `GET /api/v1/coordinator/messages` and `GET /api/v1/promote/{project}/{issue}` declare the model they answer in, and their old addresses — `/api/projects`, `/api/address`, `/api/coordinator/messages` and `/api/promote/{project}/{issue}` — answer the same body as aliases marked deprecated in the API's description, through the 0.7 series like the other aliases. Three JSON reads stay outside `/api/v1/` on purpose, and `docs/reference/the-front-end-api.md` names each with its reason: `/api/factory/{project}` (the default panel's operator cockpit), `/api/jobs/{project}/{issue}/events` (a run's raw journal rows) and `/api/preview/{project}/{unit}` (still being designed). A read added under `/api/` that is neither typed nor named there now fails the tests. The default panel keeps working unchanged (#940).
- **Every frame the API's four streams push has a published shape.** `docs/reference/events.schema.json`, beside `openapi.json`, is a JSON Schema that describes each frame as one envelope — its kind, an id, a time, the project, and the product where one applies — around the frame's own fields, typed per kind, so a front end of one's own no longer has to read the panel to learn them. The streams still send their frames as before; a stream that sends this envelope is to follow (#985).
  - **An `ack` or a `refused` on the product chat's socket says which product it answers about.** When it answers about a product the credential may read — a message sent into the subscribed conversation, a conversation that was refused, a message that broke on the server — the frame carries that product's key as `product`, so a page can tell which product an answer is about, and the stream to follow, which carries several products at once, can route it; an answer about no product, or to a credential that may not read the product area, carries none.
- **A product's knowledge is searchable through the front-end API.** `GET /api/v1/product/<project>/search?q=…&limit=…` searches one product's requirements, the decisions recorded in its documents, the documents themselves and its board's cards — the kinds a product publishes — in the same hybrid ranking the product owner's turns use (lexical, then semantic, an exact-term tier first). Each hit carries its kind, its source, its product, a snippet and its rank within that product; a line of a conversation and a model's distillate of one are never returned. A product whose semantic stage is degraded says so in the answer, the read runs under no product semaphore and records nothing, and a rank is a rank within one product — the raw score is never presented as comparable across products. A blank `q` finds nothing and asks neither the embedder nor the index; with `OPENFACTORY_PRODUCT_RETRIEVAL=off` the read searches nothing and says so in `degraded`; a `q` longer than 300 characters is refused (400), and a project with no product role is refused (404) before its index is opened, in the very words an unknown project is. `q` and `limit` are declared parameters of `openapi.json`, with the 400 and the 404 (#988).
- **A product can start before its code.** `openfactory product start <name> <context-repository>` registers a project with its context repository and no code repository (on one machine the context is created when it does not exist); its product owner's conversation, its requirements and its context work at once. Everything that needs code refuses it by name, naming the way through: every action row that needs the code (reason `no_code_yet`), pickup, `box prove`, `run`, `poll` and `project init`, and the doctor says it once, as its `code` line, which the readiness check (`env_check`) holds on. A context that already lists sources leaves the product role off for such a project, and a GitHub context counts as its organisation for the one-organisation rule. An acceptance records the promise and says its breakdown waits for the code. `openfactory product first-source <name> <path-or-url>` then asks the registry's checks, adds the code repository to `sources:` in the context and records it in the registry, and the breakdown needs no other step; a context that lists other repositories and not this one is refused, with nothing written. Both are action rows (`product_start`, `product_first_source`), reachable from `POST /api/act/{name}`; the onboarding guide says where a context comes from — created, reused or brought in (#992).
- **Requirements written elsewhere can be imported into a product, under the corpus's rules.** `openfactory act product_import` (and `POST /api/act/product_import`) takes a folder or an archive of requirements, facts and documents, shows the plan with a token, and lands it on `yes` in one commit pushed once under the product's semaphore. Every requirement is numbered after the highest number the product ever used and after any proposal still on its way, with references renumbered; the same title is the same promise — the same text adds only its missing decision rows, a new text revises a requirement nobody agreed, and a new text for an accepted one — or one whose own history reaches an accepted one — is kept in the import's record under `.openfactory/imports/<id>/` without touching the promise; the corpus is checked before the commit, and an import that would break it or change an agreed requirement lands nothing. Nothing lands as accepted, a known fact is never rewritten, documents land under `imported/` and never over an existing file, and the product's knowledge is refreshed afterwards. An import needs no code: it writes only the context — requirements, facts and documents — so it works on a product that started before its code, with a context repository and no code repository yet, as the conversation, proposals, acceptances and facts do. Only a product admin may import; from anywhere but the command line, the folder must be in the product's import inbox (#993).
- **The product role says where its requirements came from.** An import that lands is told once to the product's room — what arrived, from where, and how many requirements were added, revised or kept beside an agreed one, naming no person. While it is a review to hold, the briefing carries a line read from the newest import's record (its origin, how many are still proposed and agreed, where the design is), and what is still open — every imported requirement's open questions, the questions the import brought, the decisions its documents raise and every text kept beside an agreed requirement — is on the agenda as items to ask, closing as the requirements are accepted, dropped or replaced. The event is told from the import's record, and a retry of the same import tells it when a crash or an unreachable room kept it from being told; a text that would change an agreed requirement is said as kept beside it and asked as a yes to change. What the pack quotes from the import is fenced as quoted material, never an instruction, and bounded. The role's instructions treat an import as a review with the person who asked, and the evaluation battery has a `saltmarsh` fixture whose question is the conversation that opens after an import (#994).
- **A product can declare its own requirement template.** `template.yaml` beside the requirements lists the company's header fields (text, choice, date; required; listed) and sections; the corpus reads them into `Requirement.fields` and `.sections`, a requirement that does not meet the template is a warning (`field-missing`, `field-value`, `section-missing`), `propose_requirement` writes them, and the role's index shows the `listed` fields. The core's own header lines and sections cannot be taken, and a template that cannot be used is a `template-refused` warning with the core's shape applied. A template holds at most 50 values of 60 characters to a choice and 300 characters of `help`, beside its 30 fields, 20 sections and names of 60 characters, and one past any bound is a `template-refused` warning that names it. Also fixed: a header field is matched by its whole label, so `- **Date of go-live:**` above `- **Date:**` is no longer read as the date. ADR-0058 (#1001).
- **A product's system layer is read through the front-end API, and the product page draws it.** `GET /api/v1/product/<project>/system` answers the map the knowledge refresh publishes at `.okf/system/` in the product's context repository: the sources read, the components and the links between them, the HTTP and gRPC interfaces with their operations, the events, the databases and their schemas, the queues, the infrastructure, the decision records, and what could not be derived — every entry with the repository, file, commit and line it came from, and names only, never the value of a variable. `state` says whether the map was read (`published`), is not there yet (`not-published`) or could not be read (`unreadable`), and `why` says it in a sentence; the map's fields are null unless it was read, so a map that is not known is never answered as an empty one, and a source the refresh could not check out is answered as a `source-unreadable` entry. A map with one file that cannot be read is answered as unreadable, never with that file's parts left empty. The product page has a System tab, read when it is opened, that draws the map with what could not be derived first. A project with no product role is answered with the same 404 an unknown project gets; the read pushes nothing and files no impediment (#1002).
- **A product's knowledge can be brought up to date now, without holding a request open.** `openfactory act product_refresh --param project=<name>` (`POST /api/act/product_refresh`) reads what changed in the product's context repository as the scheduled pass does, then brings the product's search index up to those documents, the requirements and the board of every registry project of the product. It answers at once with `refresh: started`, or `joined` when a refresh of that product is already running, and the work runs on the worker, so it needs the durable engine; with none it is refused as unavailable. `product_status` now answers `knowledge`: when the index was last brought up to date, how the last refresh ended (`refreshed`, `degraded`, `failed` or `no-context`), whether the schedule or a person asked for it, each thing it did not bring up, and whether one is running. `product_ingest` is unchanged and still answers inside the request (#1004).
- **A YAML file a repository holds is read without expanding aliases, and within bounds.** Every YAML document the core reads goes through one loader. The core's own files (the manifest, `product.yaml`, the published system map, card, capability and document front matter, flows, the knowledge bundle, the registry, a rubric, a battery, thresholds and profiles) are read with anchors and aliases refused, and each reader answers such a file the way it already answers one it cannot read, with a sentence that names the anchor or alias, its line and the remedy, such as "an anchor (`&base`, line 4): this file is read without anchors or aliases — write the value out where it is used". Compose files, CI pipelines, Kubernetes manifests, OpenAPI documents and decision records, whose formats have anchors, still read them, with each alias counted at the size and depth of the value it repeats. Every document is read to 1,000,000 bytes, 100 levels of nesting, 200,000 values and 10,000,000 bytes of values with its aliases counted, and one past a bound is refused by name before anything is built from it: a `product.yaml` nested a thousand levels deep no longer raises out of its readers, and an aliased front matter is no longer written out in full when its title is read. A published system map that cannot be read is now named among the product role's blind spots for the turn, with the file and the reason, where it was treated as absent. What the core writes never carries an alias (#1005).
- **A preview comes down without docker's grace period.** Ending a preview now gives each of its containers 2 seconds to stop before it is killed, where docker granted 10, so a preview whose processes ignore SIGTERM, as a process run as PID 1 with no init does, comes down in seconds rather than tens of seconds per container. Nothing is lost by the shorter wait: the same `down` deletes the preview's volumes and the images it built. The 2 seconds is the compose runtime's default; the runtime takes a `stop_seconds` option, but no deployment setting reaches it yet (#1070).
- **Registering a project, making it ready and onboarding a product's context repository are actions.** A front end of one's own runs them with `POST /api/act/{name}`: `project_add` with every option `openfactory project add` takes, `project_init` and `product_init`. `openfactory project add`, `project init` and `product init` map onto the same rows, with their flags and exit codes unchanged, and so does the panel's `POST /api/projects`, which now writes every axis `project add` writes (#1085).
  - `project_init` and `product_init` take several steps, and `data.steps` says what each came to: done, already there, not this project's to do, or failed and why. A step that fails leaves the ones before it done and says so. Running the same command again does only what is missing: a registered project is never written over, and no board or repository is made twice.
  - `project add` is safe to run again. A project already registered as asked is a success that changes nothing, where a second run ended in a traceback; one registered differently is refused, naming what differs.
  - `product init --write` run again finds the review it already opened and updates it, where it tried to open a second and reported a failure. It runs for a product that started before its code, declaring it with no source, and refuses a `--source` there: listing one is `product first-source`'s.

### Fixes

- **Kimi Code jobs start.** `kimi-code` 0.31.1, the version the worker image installs, refused every Kimi run before calling a model, because the command carried `--auto` (and, for the planner, read-only questions and `openfactory box prove`, `--plan`) beside `-p`, which that version rejects with `Cannot combine --prompt with --auto.`; prompt mode already runs as auto on new and resumed sessions, so both flags are gone (#362).
- **Bringing a pull request up to date on the local forge no longer switches your branch.** When a job's branch fell behind, the factory rebased it in your own working tree, which left you on `openfactory/<n>` afterwards, and failed outright if you had uncommitted changes. It now rebases in a temporary tree of its own, so your current branch, your index and your uncommitted changes are left as they were, your `rebase.updateRefs` setting moves none of your branches, a `commit.gpgSign` setting no longer makes it fail, and the registrations of your own linked worktrees are never pruned. The rebased commits name the factory's bot as their committer (#622).
- **A job that continues a pull request waits for you when its branch is checked out somewhere else.** On a machine running the worktree box, an adjust, a repair or a resumed job failed with git's own sentence when the card's branch was out in another working tree, such as a tree you made to review the pull request, or your own checkout, and `resume` only reopened the gate. The job now holds, names the path that has the branch and the command that frees it, and `resume` checks again. The command keeps what you have there: on the local forge, when the job continues the pull request, commit and `git worktree remove` the tree; when the job builds the branch again (a fresh start, or any job on a hosted forge), `git switch -c` to a branch of your own. A review tree deleted with `rm -rf` still holds the branch: the card says so, and on a job that builds the branch again it first gives the `git branch` that keeps what you committed there. Nothing the job did not create is removed, a tree of the job's own that you locked is left as it is, at the start of a job and at its end, and the job no longer runs `git worktree prune` in your repository (#623).
- **A card the sizer splits keeps what its author wrote.** Each card a split creates now carries the parent card's other sections (its scope, its context and anything else written beside the objective and the acceptance criteria) under a heading that names the parent, and the job and the reviewer read them; when they do not fit in the card, they are cut with a line that says so and a link to the parent (#624).
- **A paused Codex job resumes.** In its default sandbox mode the Codex harness resumed a paused job with a sandbox flag that `codex exec resume` refuses, so the job failed at once with exit code 2 instead of continuing; a resumed session is now handed its sandbox, `workspace-write`, as a configuration override that the command accepts. Jobs run with `OPENFACTORY_CODEX_FULL_ACCESS` were not affected and are unchanged (#636).
- **The installer shows one command to start the factory, and it works.** `openfactory init`, run by the installer, also printed `docker compose --env-file /out/.env.compose up -d --build`, naming a path that exists only inside the installer's container and a build an installation from published images cannot do. The installer's own command is now the only one. Run by hand, `init` names the environment file as you passed it, from the directory you are in, and adds `--build` only in a checkout that builds its own images (#652).
- **The CLI image builds when docker/extra-ca/ holds a root certificate.** Since 0.1.0, its trust step looked for a Python module its base image does not carry, so building the CLI image from source behind TLS interception failed — the release's upgrade rehearsal, the build profile of the compose file, a deployment that builds its own images; it now adds the root to the system trust store the image already has and points pip at it, as the worker image does. The published images were built without an extra root and were never affected (#738).
- **Recreating the schedules by hand with `python -m openfactory.runtime.temporal.schedule` works again.** It stopped with a `NameError` right after the poller, so the tech-lead's rounds, the product sweep, the knowledge-map refresh and the card-question sweep were never created by it; it now creates all of them, as the worker already did at boot (#744).
- **Two projects proved at the same time no longer break each other's proof.** Every `box prove`, `box answer` and onboarding proof used one branch name, so on the worktree box a second proof could not start or removed the working tree the first was running in, and on either box a second proof of the same project removed the first one's box. Each project now proves on a branch and in a working tree of its own, and a proof of a project that is already being proven on this machine, from the same process or another, is refused with a sentence saying so instead of removing the box in use (#745).
- **A card runs again on the worktree box after git has forgotten its previous working tree, or after an earlier run was killed while git was checking it out.** When the deployment refreshed its copy of a repository, git otherwise lost track of a card's earlier working tree, or the process died in the middle of creating it, the next run of that card stopped, on git's `already exists` or on a lock nobody had made, and parked. The job now removes a leftover it can prove is its own working tree of that repository and starts, and leaves anything else at that path as it is, a lock a person made included, saying whose it is and the command that moves it (#746).
- **A job on the worktree box keeps its repository while the cache refreshes.** When the repository cache found its checkout behind the base or dirty, it swapped the checkout out, and a job whose worktree had been added to it lost its git directory mid-run: every git command failed with "not a git repository" and the finished work was never pushed. The checkout now stays in place while a job's worktree is on disk, for at most a day, and the log says which worktree is holding it (#747).
- **The panel keeps answering while the floor reads every project's box.** Reading the floor ran git for each registered project on the thread that serves the panel, so with many projects every other request waited until it finished — engine reads included, which then reported that the engine did not answer; that read now runs beside the panel rather than on it, and the floor's answer is unchanged (#748).
- **On Jira, an email and an API token of two different accounts are named as such, instead of every card reading as missing.** Jira Cloud answers a request made with another account's token as if nobody had signed in, so every card that exists came back as not found, and polls and jobs parked on it. When a card is not found, the tracker now asks Jira who is signed in. When the answer is nobody, it refuses with a sentence that says the email and the token are not one account's and how to pair them, or that no token reached it. A card that is really missing still reads as missing, and so does any card where Jira could not answer the question (#749).
- **A Claude Code run that dies before its result is parked as rate limited only when the CLI said so.** When a run was killed or stalled before the CLI printed its result, the whole transcript was searched for limit wording, tool output and the repository's own files included, so a repository about throttling (`429` handlers, quota code, a `rate-limiter` directory) parked its own runs as a usage-limit pause with a resume timer, and so did any such run whose stream carried the CLI's routine rate-limit status event. The pause is now read only from what the CLI itself said: what it printed outside the event stream, the error message it writes in the model's place (its sentence or its error code), its last rate-limit event when that says the plan is spent and no extra usage is paying (its reset time is shown), and a retry of a rate-limited request it was still making when it died. Codex, Kimi and OpenCode already read only their CLI's own words and are held to the same rule (#750).
- **A Jira ticket written in Jira's own editor keeps its Heading 2 sections and its bullets.** A description with an Acceptance criteria heading and a bulleted or numbered list reached the factory as bare lines, so it found no sections and no criteria and refused the ticket as incomplete; a Heading 2 and list items now arrive as the sections and criteria they are (a heading of any other level does not open a section yet, so write those headings as Heading 2), and a description the factory wrote to Jira reads back with its blank lines, so a split card's last item no longer swallows the line under it (#751).
- **A busy floor's job list answers inside the engine's read deadline.** The panel, the floor and the tech-lead asked the engine about each recent job one after another, so a few dozen jobs ran past `OPENFACTORY_ENGINE_DEADLINE` and every reader was then told the engine was unreachable; the jobs are now asked about `OPENFACTORY_LIST_CONCURRENCY` at a time (8 when unset), readers arriving together share one read, and a list read in the last 2 seconds is handed to the next reader on the same loop of the same process (#754).
- **A review now streams its events like every other Claude role, so a wrapper in front of `claude` sees its rate limits.** The reviewer asked the CLI for a single answer at the end, so a wrapper that rotates accounts, benches an exhausted one or audits calls never saw a review hit a limit; the review now runs with the same streaming output as the executor, and its verdict and the pull request's cost line read as before (#755).
- **On Kimi Code, a planner that writes to the job's workspace stops the job.** Its read-only role is an instruction only, and a file it wrote was committed into the pull request with the executor's work, or pushed to the job's branch when the planner then hit a rate limit. The job is now held, naming what the planner wrote, before anything is pushed, and the workspace is discarded; a workspace git cannot read holds the job too, in git's own words. This applies only to projects that turned `planner_stage` on (#788).
- **A card GitHub would accept is created whatever its script.** The GitHub tracker passed a new card's body as a command-line argument, which Linux refuses from 131,072 bytes on, so a body within GitHub's 65,536 characters failed to create once it was long and written mostly in a script of three or four bytes a character — Chinese, Japanese, Korean, Thai or emoji — and since a split card's children carry their parent's other sections, a split could fail partway; the body now goes to `gh` on standard input, as an edit's already did (#807).
- **A `product.yaml` key that is not a string is named instead of crashing the reader.** A key of `.openfactory/product.yaml` that YAML reads as something other than text, such as `1:`, `on:` or `yes:` (YAML reads both as true), `~:` or a date, written there or merged in with `<<`, made every reader of the file raise an error, so the product module and a product's preview failed instead of saying which file to fix; a list or a mapping written as a key was refused, but in the YAML parser's own words, naming no key. Each is now one sentence that names the key as written, its line, what YAML reads it as and the remedy, for example `.openfactory/product.yaml is invalid at 'on' (line 3): a key must be a string, not !!bool; quote the key if it is meant as text` (#819).
- **A working tree under a directory the factory cannot search is no longer reported as gone on Python 3.14.** When a card's branch is checked out in a tree inside a directory the factory has no permission to enter, the factory could not tell whether the tree was still there. On Python 3.12 it held the job and named the tree. From Python 3.14 it called the tree gone and told the person to remove it. It now holds the job on every Python version and treats a tree as gone only when it could look and found nothing there (#827).
- **The stack preflight and `openfactory doctor` send a missing agent credential to the credential store you declared.** When `.env.compose` sets `OPENFACTORY_CREDENTIAL_STORE` to a store other than `env`, `openfactory preflight` no longer says to put the token in `.env.compose`. It says the credential is expected in that store, that the preflight does not read the store, and that `openfactory doctor` checks it once the stack is up. The doctor's own remedy for the missing credential names the same store, and for `file` the directory `OPENFACTORY_CREDENTIAL_DIR` names, instead of `.env.compose` (#904).
- **`openfactory bot-token --key-path <file>` signs with the key in that file.** The option was accepted and ignored: the key always came from `OPENFACTORY_GH_APP_KEY_CONTENT` or `OPENFACTORY_GH_APP_KEY`, so a new `.pem` could not be proven before it was deployed. An explicit path now wins over both, a path that is empty or cannot be read is refused by name, and without the option the key is found as before (#905).
- **A product refusal answers as a refusal, not as an internal error.** When the product role declines a write on purpose — the card is not yours to withdraw, it is already closed, the requirement does not exist — the action now answers 403, 409, 404 or 400 with the role's own sentence and the role's reason in `data.refusal`, where it answered 500; a write that was tried and did not happen is still a 500, and carries in `data.reference` the reference its log line names (#908).
- **A symbolic link that points to itself where a working tree of a repository used to be no longer stops that repository's jobs on the worktree box with a traceback.** On Python 3.12, the oldest Python the factory runs on, every job on the repository failed as it started with `Symlink loop from …`. A job whose branch that tree does not hold now starts, and a job whose branch it holds waits for you and names the tree, as for any tree the factory cannot look at, without calling it gone. A directory at the job's own path whose `.git` file names a path through such a link now stops the job with the factory's own sentence, which names the directory and the command that moves it aside, instead of `Symlink loop from …` (#939).
- **On Kimi Code, a planner stopped at the wall-clock wall now holds the job before the executor runs.** The wall stops only the shell the box started, so the stopped planner could keep writing into the workspace the executor then commits, and a file it wrote after the check had read the tree reached the pull request. The job is now held, naming the walled planner, before anything is pushed, and the workspace is discarded. This applies only to projects that turned `planner_stage` on (#980).
- **A Kimi planner that leaves the job's workspace unreadable is held as the planner's doing, not as a broken box.** When git could read the workspace before the planner's pass and cannot after it, for example because the planner ran `git init` in a subdirectory, the job is held saying that the workspace became unreadable during the planner's pass and that the planner is the likely cause, with git's own exit and words, and the hold declares the same cause as the hold for a planner that changed the workspace. It no longer declares an environment fault telling you to "Make git usable on this workspace in the box". A workspace git cannot read before the pass is still held as the environment, as before (#981).
- **A requirement's own text can no longer write a heading into it.** A line break in a drafted requirement's title, *Why*, a criterion, an out-of-scope line, an affected path, an open question or a conflict could open a line such as `## Decisions taken during execution`, and the corpus read that one as the decision register: the requirement counted a decision nobody took, and the next decision was written into it. The title and every bullet are now written on one line, and a line of a section's text that would open a heading is written with `\#`, which Markdown shows as the `#` outside a code block (#1086).

### Security

- **The shared panel token can no longer invite people.** A caller holding only `OPENFACTORY_PANEL_TOKEN` was treated as a person called "panel", so its invitations went through as if somebody had vouched for them. It is now anonymous all the way to the action layer, and `people_invite` refuses it with "an invitation records who vouched for the person, and nobody did". A named row in `OPENFACTORY_PANEL_TOKENS`, a registered person and an SSO login invite as before (#759).
- **A shared board or product token keeps its scope however it is presented.** `OPENFACTORY_BOARD_TOKEN` and `OPENFACTORY_PRODUCT_TOKEN` now act only in their own area whether or not a request sends an `X-OpenFactory-Actor` label, and whether the token comes in the `Authorization` header, the credential cookie or `?token=`; a request without the label, or a read presenting the token by cookie or query, was treated as the unscoped panel token. Details in the advisory (GHSA-6f99-wwgx-6q52).
- **A label sent with a shared credential no longer names who acted.** The `X-OpenFactory-Actor` header is now only a label the action audit line prints: an answer to a question on the panel and a pressed proposal are recorded under the shared credential's own name, such as `somebody with the panel token`, and the product gate is never asked about the label as one of the product's approvers or as the person who asked. Details in the advisory (GHSA-qmfq-gv34-579p).

### Upgrade notes

- **A project whose documents pass 160,000 bytes now hands its agents fewer of them inline.** Every record left out is named in the prompt by its path, so the agent can open it; set `OPENFACTORY_PROMPT_BUDGET` to a larger number of bytes, or to `off` to inline everything as before, and run `openfactory doctor` to see what a pass keeps (#364).
- **The reads of the API are served under `/api/v1/`, and their old addresses are deprecated.** Each read that declares its shape — the floor, the jobs, a job's detail, the board, attention, the inbox, the budget, the decisions, the loops, the messages, the product room, its documents, the metrics, whoami and the action catalogue — answers at `/api/v1/…`, and its address without `v1` answers the same body as an alias marked deprecated in the API's description. The aliases answer through the 0.7 series and are removed no earlier than 0.8.0, so a screen of one's own should call `/api/v1/` now; the default panel keeps working unchanged. The description is committed as `docs/reference/openapi.json`, with the package's version, and `docs/reference/the-front-end-api.md` says the deprecation policy (#678).
- **The durable runtime now needs `temporalio` 1.29 or later**, where it accepted 1.7. A process now holds one engine client and hands it to every caller on any event loop, which relies on a change in that release. An installation that pins `temporalio` below 1.29, through a constraints file or a distribution's package, must raise the pin before it upgrades (#681).
- **Who may act, and who approves production, is proposed to become one decision the core makes (ADR-0057).** Nothing changes in this release. The record proposes that a production release is approved by the signed-in person holding an `approver` role, with a fresh sign-in, and that `~/.openfactory/approvers.json`, `OPENFACTORY_APPROVERS` and `openfactory approver` retire over three releases. It also lists how today's panel, board and product tokens, OIDC groups, `project.admins`, `product.admins` and `prod_approvers` would map onto roles on upgrade, so that nobody loses access silently. Read it before you add approvers to the password store (#690).
- **Nothing changes for an installation that declares no credential store**: with `OPENFACTORY_CREDENTIAL_STORE` unset every credential is read from its variable, byte for byte, as before. The worker, the panel and a remote box no longer copy a GitHub App key handed over as content into a temporary file at start-up, and no longer set `OPENFACTORY_GH_APP_KEY` to point at it; the key is read as content, as it already was (#742).
- **A deployment whose registry spans two GitHub organisations now fails `openfactory doctor`.** The same holds for a deployment whose GitHub projects use the App and whose App is installed on another organisation than the one the registry names: the project reads NOT ready, and the doctor control of a certificate is red. Run one deployment per organisation, or remove the projects that belong to the other one (#743).
- **An existing board keeps putting a pull request that waits on a person in Needs Action until you give it a Needs Review column, and a column already called `Needs Review` changes meaning on some boards.** (#753)
  - To opt in on the platform's own board, re-run `openfactory project init`: it adds Needs Review between In review and Needs Action, renames nothing, and puts the platform's columns back in board order only when it added one. When another column of the project is already called `Needs Review` (in any case), it adds none and names that column; to opt in there, map `needs_review` to another name under `columns`.
  - On GitHub Projects, add a Status option named `Needs Review` by hand, or name yours under `columns`. A board that already has an option named exactly `Needs Review` starts receiving these pull requests with no configuration change.
  - On Jira, name the status under `status_map`; on Azure Boards, name the column under `columns` and the state under `state_map`. The factory moves cards into it only when the map names it, but a status already called `Needs Review` is now read as the review wait wherever a person puts a card: before, it was unmapped, the doctor's `board_stages` listed it and the board's actions on a card in it were refused, as in any column nothing maps; now a card in it can be moved back to the queue when no job waits on it.
  - The name `Needs Review` is `needs_review`'s only while the map gives it to no other key: a park already called `Needs Review` (`needs_action` mapped to it) is still read as a park, and a review column already called `Needs Review` (`in_review` mapped to it) is still the factory's review, so the factory sends a pull request waiting on a person to Needs Action there, not into it. Two keys mapped to one status (`in_review` and `needs_review` both `In Review`) read back as `in_review`.
  - Opting in moves no card: a pull request already in Needs Action waiting on a person stays there until the factory next moves it (a re-review sends it to Needs Review; the merge sends it to In review, and it reaches Done once the change is delivered, at once when the project's `.openfactory/project.yaml` declares no `post_merge_deploy:` and no `environments:`); on GitHub Projects, Jira or Azure Boards you can also move it to the new column by hand.
  - For the authors of an add-on board or tracker: `column_key(PR_OPEN, needs_person=True)` now answers `needs_review`, and only `column_keys` applies the fallback to `needs_action` (`FALLS_BACK_TO`). A row that calls `column_key` itself and maps no `needs_review` leaves such a pull request where it was instead of moving it to Needs Action; map `needs_review`, or resolve through `column_keys` and take the first key the board has.
- **On a deployment that signs people in through an identity provider, everyone whose groups map to no area is the administrator, and can now pause pickup, revoke a person and name or declare a product from the panel.** They could already invite people there. Before upgrading, map the provider groups that should be the board's or the product's in `OPENFACTORY_OIDC_GROUPS` (`OF-Board=floor,OF-Product=product`), so that only the administrators are left unmapped (#839).
- **A preview is never handed a variable a harness route requires, and one already in a project's preview policy is dropped when the registry is read.** `OPENAI_API_KEY`, `AZURE_API_KEY`, `AZURE_RESOURCE_NAME`, `AWS_REGION`, `AWS_DEFAULT_REGION`, `CLOUD_ML_REGION` and `VERTEX_REGION` join the factory's own credentials on the list a preview is refused, on either side of a `svc=NAME=WORKER_NAME` mapping: a preview runs code from a pull request nobody merged, and its policy can now be set from the panel by every credential that is the administrator there — the panel's token, a person invited to neither area, and on an identity provider everyone whose groups map to no area. A service of a preview that read one of these names receives nothing under it now; give it the value under a name of its own (#840).
- **Discarding a file from the project's room needs a product admin, however the request reached it.** A caller with no conversation of its own (an API token, the CLI) reaches the project's room whatever it asks for, and could discard the room's files without being on `product.admins`; it is now refused with "a file in the project's room is everybody's — a product admin takes it out." To discard such a file, be listed on the project's `product.admins`, or discard from your own conversation (#997).
- **A core file that uses YAML anchors or aliases must be written without them.** A `.openfactory/` manifest, a `product.yaml`, a card's or a document's front matter, a profile or the project registry that defines `&name` and reuses it with `*name` or `<<: *name` is now refused with a sentence naming the anchor and its line; write the repeated value out in each place it is used. Compose files, CI pipelines, Kubernetes manifests and OpenAPI documents keep their anchors (#1005).
- **A credential scoped to the board can no longer register a project, initialise one, onboard a product's context repository, start a product before its code or give one its first source.** These rows change the installation, so they are the administrator's alone, like the other installation rows: the panel's token and its per-person rows, a person invited to neither area, and on an identity provider everyone whose groups map to no area. That includes `POST /api/projects`, which a board token could call before and which now answers it with a 403. The same door now registers an Azure DevOps clone URL on both axes, and refuses one that does not carry its coordinates with a 422; before, it wrote the tracker axis alone (#1085).

### Known limitations

- **On Kimi Code, the planner and read-only questions are read-only by instruction only.** `kimi-code` 0.31.1 refuses plan mode beside a prompt and has no sandbox-policy flag, so nothing but the instruction keeps those roles from writing. The planner runs on the job's own workspace, and a planner pass that writes there holds the job. The read-only questions (the sizer, the tech-lead, the product role, card drafting and judging, documents) run on the host whatever the sandbox setting, in a directory nothing commits from, except `env context --ask`, which asks in the checkout it is pointed at, where a write is left in that working tree, and the independent review, which runs in the job's box on the job's workspace before the push, where its write can reach the pull request; nothing confines a write to any of them. A per-run agent file with a `tools:` list would enforce it and is not used yet. Give the executor (which also plans), the reviewer and the judging roles another harness where that matters (#362).
- **Under a Jira `scope_jql`, the tickets the factory creates must match the scope by other means.** Its create writes only the project, summary, description and issue type, so a split's children, the product role's cards and its impediments carry no label of the scope: outside it, the poller does not pick them up, the panel and the product role do not show them, and the search for an earlier filing does not find them, so a retry files another, and a scoped project refuses to edit, close, remove, queue or rank them until they are. Scope by something every new issue of the project receives, such as a label or component a Jira automation rule sets on each issue the project's own account creates; `docs/reference/configuration.md` says how (#752).

### Highlights

- **One release a week.** The cut and the first candidate on Monday, the final on Wednesday. What is merged by Monday's cut ships that Wednesday; what is not ships the week after (#530).

- **The PyPI page describes the project.** It says what OpenFactory is and is not, how to run it on one machine or as a team deployment with Docker, where each coding agent stands and what the extras add, and the suite holds every claim on it true (#368).
- **A release's notes are in `CHANGELOG.md`, and on its page.** Each pull request carries the line the notes will read for it, as a fragment in `changes/`. The final release assembles them into `CHANGELOG.md`, and its GitHub page carries them under the install block. A candidate's page carries the notes so far (#517).

  - docs/RELEASING.md says how to back up an installation before trying a candidate, and how to go back: the two files, the Docker volumes and the two host directories the stack writes, with the commands.

It fails at half of it, at a hundred zombies, or when a running container is asked and does not answer, and it gives the repair. Each line names the container as its service declares it, with the new `OPENFACTORY_ROLE` that the compose file sets to `worker` and `panel` (#532).

The developer guide that teaches it is run by the suite (#548).

- **`openfactory certify verify` checks a pack offline, and the pack measures its outcomes.** `verify` checks a pack the way the submissions bot does, its files, schema, checksums, signature and every threshold, each reported by id. The pack's outcomes over its window, from jobs and how they ended to cost per merged ticket, are read from the journals and the metrics store: a measure that cannot be read is null with its reason, never zero (#554).
- **The panel's page can be turned off.** `OPENFACTORY_DEFAULT_FRONT_END=off` serves the API, its two streams, the sign-in and the previews, and no page, for a deployment with screens of its own built on the same API. It is `on` by default, so an upgrade keeps the panel, and `openfactory init` writes the line (#611).
- **The API a screen of your own can rely on is documented.** `docs/reference/the-front-end-api.md` lists every route with the area a credential must hold, the three ways to present a credential, the refusals and the streams. A test keeps it equal to the code, and the panel uses nothing outside it (#612).
- **A credential for the board, and the product owner reads the board.** `OPENFACTORY_BOARD_TOKENS` / `OPENFACTORY_BOARD_TOKEN` and `openfactory people invite --board` issue a credential for the board and the rest of the floor, which is refused the product owner's area by name. The panel token stays the administrator's and reaches both, and inviting somebody stays the administrator's. A product credential now reads the board of a project with a product role, read only (#613).

A page whose credential changes under it in another tab opens again as the page that credential may see (#614).

The page asks first, because from the queue the factory picks the card up and starts spending. Anyone else sees, in place of the button, that starting is an approver's yes (#637).

The cards are now ranked on the board in the approved order, and the reply says when a board cannot rank or refused a rank (#512).
- **Every answer to the product role's writes speaks the conversation's language.** Refining, closing, removing, correcting or aligning a card, a capability, a breakdown, a queue and the release's refusals answered in Portuguese only, and some named a Jira card `#KEY`; they now answer in the conversation's language and name a card as its tracker does (#513).
- **On Jira, a backlog order is stated by the cards' keys.** The order a person confirmed in the conversation was read as digits only, so an order of Jira keys could not be stated; it is now read by the tracker's own keys (#515).
- **A card in a column no stage is is refused with the line that maps it.** On an Azure DevOps board with a stock process every new work item lands in `New`, which maps to no stage, and the first card's queueing was refused in English with no fix named. - **The installer's preflight reaches Docker Desktop's daemon.** On macOS with Docker Desktop the preflight said the daemon did not answer, one step after the installer had pulled every image through it, and skipped the two checks that need it: the preflight's container was given the host socket's group, while Docker Desktop hands a container a socket owned by group 0. The installer now gives it the group a container sees, and a refused socket is named as a refusal, not as a daemon that gave no answer (#529).
